# Proposal, HLD & Incident Report HTML Architect (`prop-hld-ir-html`)

IT現場で使われる文書の読み手は、基本的に**「判断したい」**人です。  
本スキルは、`it_document_style_guide.html` を原典とし、提案書（Proposal）、基本/方式設計書（High-Level Design: HLD）、障害・調査報告書（Incident Report: IR）などの重要実務文書において、装飾ではなく**「構造と図表の精度」**によって読み手の判断速度を最大化するHTML技術文書の作成規約と設計標準を提供します。

---

## 1. コア原則（Core Principles）

### 1.1 装飾3要素の可否判定
1. **グラデーション**：本文中では原則使用禁止。表紙・章扉のみアクセントとして極めて抑制的に許可（公共・金融・医療・官公庁向けは全面無地）。
2. **絵文字**：IT文書（仕様書・報告書・提案書）では**全廃**。検索性（grep/検索機能）、コピー＆ペースト、アクセシビリティ（スクリーンリーダー）、正確性を破壊するため。
3. **アイコン付き3枚カード**：**アイコンを外し「3点整理（1. 2. 3.）」**として活用する。アイコンはLP的で社内・技術文書から浮くが、「論点は3つ」という構造化自体は意思決定において極めて有効。

### 1.2 装飾の代わりに使う代替文法
* **階層は文字サイズと余白**：見出し番号（`01`, `1.1`）＋フォントウェイト＋上下余白で階層を確立。枠や塗りに頼らない。
* **関係は図で、数は表で**：インラインSVG、関係図、比較表を徹底活用する。
* **強調は色ではなく比較**：赤字やマーカーではなく、「A案 vs B案」の対比グリッド（`.split`）や比較表で示す。
* **各章に「結論ボックス」を1つ**：`class="conclusion"` を章冒頭に配置し、本章のメッセージを1文で明示。
* **図解のスタイル基準（Type A: 実務・意思決定型）**：
  - **インラインSVG & CSSネイティブ限定（Mermaid完全排除）**。
  - **紙と墨・モノクロ基調＋朱色（`#b5371f`）1色のハイライト**。カラフルな塗りやグラデーションは厳禁。
  - **印刷（白黒）最適化と凡例（Legend）の義務付け**：主観的誇張を排し、シーケンス図・状態遷移図・ER図・因果フローを正確に描く。
* **完全自己完結型（Zero External Dependency）**：外部CDN、外部Webフォント、外部JavaScriptに依存せず、ブラウザ単体やオフライン環境、ローカルファイルとして即座に破綻なくレンダリングされること。

## 2. 文書種別ごとのスタイル判定マトリクス

| 文書種別 | グラデーション | 絵文字 | 3枚カード | スタイル方針 & 実務指針 |
|:---|:---:|:---:|:---:|:---|
| **提案書（社外・経営層）** | △ | × | ○ | 表紙のみ落ち着いた単色。本文は3点整理＋比較表。アイコンは外し番号付きにする。 |
| **技術提案・RFP回答** | × | × | △ | 番号付き箇条書きに置換。評価要件一覧と対応表を最優先。 |
| **報告書（障害・調査・進捗）** | × | × | × | 時系列（Timeline）と因果関係が主役。等分カードは因果を平坦化するため禁止。 |
| **仕様書（要件・設計・API）** | × | × | × | 装飾ゼロ。図はインラインSVGまたは標準HTML構造で描き、凡例・用語定義を必ず添える。 |
| **説明資料（社内説明・研修）** | △ | △ | ○ | 章扉にアクセント1色。要点スライドのみ3点整理。絵文字は社内カジュアル限定。 |
| **社内Wiki / README** | × | ○ | △ | 絵文字は可。ただしコマンド・ファイルパス・IDの直近には置かない。 |

## 3. デザインシステム & CSSトークン規格

スタイルはインライン `<style>` に記述し、以下のトークン定義を厳格に順守します。

```css
:root {
  --paper: #fbfaf7;         /* 和紙を想起させる柔らかな生成り色 */
  --panel: #f2f0ea;         /* 表見出しやコードブロックの背景色 */
  --ink: #15171c;           /* 主文字色（純黒ではなく深い墨色） */
  --ink-2: #31353d;         /* 本文・説明用テキスト色 */
  --muted: #666c76;         /* 補足・注釈・キャプション色 */
  --rule: #d6d1c6;          /* 境界線・区切り線（薄） */
  --rule-2: #b9b2a3;        /* 境界線（強調） */
  --accent: #b5371f;        /* 朱色アクセント（1色に限定） */
  --accent-soft: #f6e7e3;   /* 朱色ソフト背景 */
  --ok: #2c6a4f;            /* 肯定判定・適合（深緑） */
  --warn: #8a6413;          /* 注意・条件付き適合（飴色/アンバー） */
  --maxw: 880px;            /* 視線移動が疲れない最大本文幅 */
  --font-body: "Hiragino Sans", "Yu Gothic UI", "Noto Sans JP", system-ui, -apple-system, "Segoe UI", sans-serif;
  --font-mono: ui-monospace, "SFMono-Regular", Menlo, Consolas, monospace;
}
```

## 4. 必須コンポーネント仕様

### 4.1 表題・ヘッダー（Header）
```html
<header>
  <div class="wrap">
    <p class="doc-label">SYSTEM SPECIFICATION · ARCHITECTURE DECISION</p>
    <h1>システム更改におけるデータ連携基盤 方式設計書</h1>
    <p class="abstract">
      本資料は新旧基盤間のリアルタイム同期プロトコルおよび障害時のデータ整合性担保方針を定義する。
      結論として<b>CDC方式を採用し、バッチ転送は廃止</b>する。
    </p>
  </div>
</header>
```

### 4.2 本章の結論（Conclusion Box）
各セクションの冒頭には必ず1つの結論ボックスを設けます。
```html
<p class="conclusion">
  本章の結論：メッセージ重複を防ぐため、冪等性キーをヘッダーに含めることを必須とする。
</p>
```

### 4.3 2ペイン比較グリッド（`.split`）
「A案 vs B案」や「採用理由 vs 棄却理由」を並列対比します。
```html
<div class="split">
  <div class="col-a">
    <h5>採用（A案: イベント駆動）</h5>
    <ul>
      <li>データ鮮度がミリ秒単位で維持される</li>
      <li>耐障害性が高く個別再送が可能</li>
    </ul>
  </div>
  <div class="col-b">
    <h5>棄却（B案: 定周期バッチ）</h5>
    <ul>
      <li>夜間バッチ突き抜けのリスク残存</li>
      <li>障害発生時のリカバリ範囲が肥大化</li>
    </ul>
  </div>
</div>
```

### 4.4 レスポンシブ対応表（`.tbl-wrap` & `data-label`）
モバイル画面幅（640px以下）で横スクロールを発生させず、自動的に1行＝1ブロックの縦積みに組み替えるため、各 `<td>` に `data-label="列見出し"` を付与します。
```html
<div class="tbl-wrap">
  <table>
    <caption>表1: 非機能要件適合マトリクス（凡例：○＝適合、△＝要検討、×＝不適合）</caption>
    <thead>
      <tr>
        <th scope="col">要件項目</th>
        <th scope="col" class="mid">判定</th>
        <th scope="col">備考・仕様根拠</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <th scope="row">スループット性能</th>
        <td class="mid" data-label="判定"><span class="mark y">○</span></td>
        <td class="note-cell" data-label="備考・仕様根拠">ピーク時 5,000 req/sec を実測検証済み</td>
      </tr>
      <tr>
        <th scope="row">フェイルオーバー時間</th>
        <td class="mid" data-label="判定"><span class="mark t">△</span></td>
        <td class="note-cell" data-label="備考・仕様根拠">DNSキャッシュ依存により最長60秒を要する見込み</td>
      </tr>
    </tbody>
  </table>
</div>
```

### 4.5 リーダー数字付き代替文法リスト（`ol.grammar`）
```html
<ol class="grammar">
  <li><strong>階層は文字サイズと余白</strong> — 色や枠ではなく余白で構造を伝える。</li>
  <li><strong>関係は図で、数は表で</strong> — 比較表とインライン図解で判断を加速する。</li>
  <li><strong>強調は色ではなく比較</strong> — 複数案のトレードオフを客観的に並べる。</li>
</ol>
```

## 5. 出力ワークフロー & 生成チェックリスト

HTMLドキュメントを出力する際は、以下のチェックリストを必ず確認してください：

1. [ ] **DOCTYPE & メタ宣言**: `<meta charset="utf-8">`, `<meta name="viewport" content="width=device-width, initial-scale=1">` が含まれているか。
2. [ ] **装飾の排除**: 本文中に絵文字や不要なグラデーションが含まれていないか。
3. [ ] **3点カードのアイコン排除**: 3分割要素がある場合、装飾アイコンを付けず「番号＋見出し＋要約」になっているか。
4. [ ] **各章の結論**: 各 `<section>` の先頭に `<p class="conclusion">` が配置されているか。
5. [ ] **モバイル表示最適化**: 全ての `table td` に `data-label` が設定されているか。
6. [ ] **印刷メディアクエリ**: `@media print` に `page-break-inside: avoid;` 等の印刷崩れ防止スタイルが含まれているか。
7. [ ] **外部非依存性**: 外部スクリプト、CDN、Webフォントを読み込まず、スタンドアロンで表示できるか。
